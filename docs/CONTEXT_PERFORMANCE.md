# 上下文发送前检查的性能验证

2026-09-25，本机合成会话：80 轮用户请求、720 条上下文事件，SQLite 内存数据库。
完整测量数据见 [performance-context-local.json](performance-context-local.json)。

| 测量项 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 单次检查的本地进程 CPU 时间中位数（3 次） | 2.140625 秒 | 0.0625 秒 |
| token 估算调用次数 | 32,408 | 729 |
| token 估算扫描字符数 | 11,753,621 | 274,757 |
| 历史加载的 Python 分配峰值 | 43.17 MiB | 2.71 MiB |

CPU 测量不含模型推理、网络等待、冷启动或首次加载 tokenizer。前后上下文用量、分类明细、压缩判断和压缩后预测值相同。时间结果会随机器负载变化。

内存对比为单独测量：每条历史消息含两份 128 KiB 的 HTML 快照，比较原路由先加载完整消息行与直接读取上下文事件两条路径。两者使用相同的优化后上下文构建器，用 `tracemalloc` 测量数据库初始化之后的 Python 分配峰值；该数字不是服务器总内存、进程 RSS 或生产环境测量。

实现涉及：

- 压缩保留边界使用后缀 token 累计值，避免逐边界重复扫描整段历史。
- 单个上下文构建器复用事件估算、固定提示估算和存储统计，缓存不跨请求保存。
- 上下文接口与发送流程直接读取事件账本；缺少账本时才加载旧消息的正文、角色和图片引用，避免读取历史 HTML 快照、推理记录及展示日志。
- 同一轮中，文档 revision 和工具结果预算不变时复用系统消息；没有选区时跳过图片清单扫描。
- 同一次上下文准备中，共享存储对象的历史附图只读取和编码一次，保留各条消息中的图片内容和附件引用，准备结束后释放缓存。

复现优化后基准（在 `backend` 目录执行，使用已安装项目依赖的 Python）：

```sh
python scripts/benchmark_context_preflight.py --ui-payload-kib 128 --output ../tmp/context-performance.json
python -m unittest tests.test_context_performance
```

历史图片回退编辑直接使用既有附件引用；实际再次发送时创建独立的消息绑定，共享原文件，不重复上传。删除引用时会检查是否仍有其他引用，数据库升级包含 `object_key` 唯一索引改为普通索引的迁移。
