# Agent 重试与恢复

## 设计与源码依据

重试以可安全重放的操作为边界，统一执行错误分类、带抖动的指数退避、服务端等待提示、次数与时间预算以及取消。模型 SDK 重试保持关闭，避免 SDK 与应用层倍增请求。

本次读取的源码快照：

- [Codex responses_retry.rs](https://github.com/openai/codex/blob/bfdbf01bfaeaa6ab23b10e2bd64ed031fd1e5619/codex-rs/core/src/responses_retry.rs)：推理与压缩共享恢复思路、可见重连、尊重服务端等待。项目保留有界重试，没有采用可选的无限连接重试。
- [OpenCode model-retry.ts](https://github.com/anomalyco/opencode/blob/6d1c444b8c53da667b51ed45b0a7c0aca1174674/packages/core/src/model-retry.ts) 与 [runner/retry.ts](https://github.com/anomalyco/opencode/blob/6d1c444b8c53da667b51ed45b0a7c0aca1174674/packages/core/src/session/runner/retry.ts)：退避、抖动、Retry-After 下限、重试期限与可取消等待，以及付费操作的重放边界。
- [Gemini CLI retry.ts](https://github.com/google-gemini/gemini-cli/blob/0ac57c029b848d109eef940afe0db4b5a0c3dad0/packages/core/src/utils/retry.ts)：取消信号、重试回调、嵌套网络错误与永久额度错误分类。

这是针对本项目的组合实现，并非复制某个 Agent 的全部行为。

## 行为矩阵

下表中的次数包括首次请求；时间预算限制继续发起重试，并非强行中断已执行的请求。单次调用还受原有模型、网络与运行超时约束。

| 操作 | 默认总请求次数 | 本地退避 / 单次等待上限 | 继续重试的时间预算 | 重放边界 |
| --- | --- | --- | --- | --- |
| 模型推理 | 3，可配置 | 1.5 秒起，指数增长，50%～100% 抖动 / 60 秒 | 600 秒，可配置 | 仅未完成模型轮次；撤回该轮局部输出，保留已完成工具 |
| 自动、运行中、手动压缩 | 每批最多 3 | 1 秒起 / 60 秒 | 每批 600 秒；每次调用最多 300 秒 | 只重试当前摘要批；全部批次成功后推进快照 |
| 创建任务 | 最多 3 次尝试 | 10 秒起，50%～100% 抖动 / 60 秒 | 600 秒；单次创建等待 180 秒 | 重试前先按原 client_request_id 查询，已有任务直接恢复；未找到才用同一编号重发 |
| 提交用户确认结果 | 3 | 0.5 秒起 / 30 秒 | 90 秒；连接响应超时 20 秒 | 相同问题、相同回答、相同 client_request_id |
| 停止任务 | 3 | 0.5 秒起 / 5 秒 | 35 秒；单次连接响应超时 10 秒 | 同一 run_id 的幂等取消 |
| SSE 输出重连 | 初次连接 + 最多 12 次重连 | 0.4 秒起 / 15 秒 | 连续故障 180 秒 | after=最后已消费序号；先查持久任务状态 |
| 搜图、公开网页、图片、图片代理读取 | 每个远端读取最多 3 | 0.5 秒起 / 10 秒 | 每个读取 45 秒 | 只重新读取资源，不重跑整个写入工具 |
| 写文档、应用图片、图片生成、发布 | 不新增通用自动重放 | 沿用各业务的冲突处理与显式恢复 | 业务边界 | 结果不明时禁止因网络错误盲目重复执行 |
| 数据库与身份认证 | 保留已有专项恢复 | 事务断连、事件序号冲突、单飞刷新令牌 | 原有专项边界 | 不把任意数据库写入纳入通用重试 |

下载原图失败后，已有的受控代理回退仍可执行；原图与代理各有自己的读取预算，没有在同一读取上再叠加旧的固定等待重试。

### 错误与等待

- 408、临时 429、5xx、连接中断、超时可重试；嵌套 cause/context 保留状态和响应头。`x-should-retry: false` 禁止重试。
- 400/401/403/404/409/413/422 等请求错误立即失败。识别出的余额不足、永久额度耗尽和上下文超限不做相同请求重试；上下文超限仍走已有的压缩恢复路径。
- 空模型流可以重试；流无法可靠关闭时不再启动新流，防止多个请求同时运行。
- 摘要结构无效可重新生成；本地配置或参数 ValueError 不因“格式修复”而重试。
- 支持 `Retry-After` 秒数及 HTTP 日期、`retry-after-ms`、`x-ms-retry-after-ms`。后端还读取兼容供应商错误体中的 `retry_after`。
- 实际等待取服务端建议与本地退避的较大值。服务端等待超过该操作允许的上限时，结束自动重试，避免截短后提前请求。
- 浏览器断开 SSE 只断开订阅，后台任务仍可继续。显式停止通过持久 run_id 取消后台生产者，退避 sleep 随任务取消。创建响应尚未确认时，已有的“拿到 run_id 后停止”机制继续生效。

### 前端状态

`retry_status` 提供 operation_id、scope、phase、attempt、max_attempts、delay_seconds、retry_at、reason 和 detail。生命周期为 waiting → attempting → recovered / exhausted。兼容旧的 model_turn_retry，用它撤回未完成轮次。

界面显示“第 2/3 次请求”、实际等待倒计时与操作类别。倒计时到零仅表示等待期限已到；收到 attempting 后才显示正在请求。重放事件按照事件年龄还原倒计时，旧操作的成功事件不清除较新操作的提示。

SSE 的失败计数只在收到近期实际输出或连接健康持续至少 10 秒后重置。反复收到旧状态、重试事件、单个心跳不能无限重置预算。重连会先查任务是否完成或正在等待用户，避免只依赖最后一帧。读取 Chat JSON 状态接口也增加了 20 秒的连接响应超时。

创建任务的等待独立于 SSE 连接和状态读取：每次 POST 最长等待 3 分钟，避免资源准备和上下文预检尚未完成就过早中断。首次失败后通常等待 5～10 秒，第二次失败后等待 10～20 秒；服务端建议可延长到 60 秒。每次恢复尝试先查询原请求编号：查到任务就直接使用，明确未找到才重发同一编号；状态查询失败时不发新的创建 POST，该次尝试计入总预算。用户确认结果提交仍保持原来的 20 秒单次等待。界面在创建期间显示“正在创建任务”及资源、上下文准备提示，不把正常等待显示成模型生成或重试失败。

手动压缩保留原 JSON API；前端使用同一端点的 `?stream=true` 接收重试状态及最终 context_stats。流生产者拥有独立数据库会话，断线会取消尚未完成的压缩；已提交的完整快照仍然有效。这个 POST 不做浏览器级自动重放，连接中断后需要刷新状态再确认结果。

## 场景

1. 模型限流并返回 Retry-After: 7：界面显示第 2/3 次请求、约 7 秒倒计时；随后显示正在请求；成功继续原任务。之前完成的文档写入不会重做。
2. 模型输出到一半断开：撤回该模型轮次的临时文字和待执行工具预览，再重试本轮。已落地的历史工具结果仍保留。
3. 压缩第 4 批返回错误 JSON：只重新生成第 4 批；若最终仍失败，不推进快照覆盖范围。自动压缩与手动压缩都能显示该阶段的重试状态。
4. SSE 断开：从最后序号补拉输出，不重新创建任务；如果查到任务已经完成，直接从持久状态恢复界面。
5. 429 实际是 insufficient_quota，或 Retry-After 要求等待 900 秒：停止自动重试并交给原有错误/终态处理，不在几秒后再次请求。
6. 用户在退避时点击停止：已有 run_id 的任务通过取消接口终止后台 sleep 和生产者；浏览器订阅取消不会触发新的模型重试。

## 配置与验证

模型设置来自 `backend/app/core/config.py`：CHAT_AGENT_MODEL_RETRY_MAX_ATTEMPTS、CHAT_AGENT_MODEL_RETRY_BASE_SECONDS、CHAT_AGENT_MODEL_RETRY_MAX_DELAY_SECONDS、CHAT_AGENT_MODEL_RETRY_MAX_ELAPSED_SECONDS。变更这些环境变量需按项目原有方式重新加载进程。

测试涵盖 HTTP 日期/毫秒、抖动上限、永久错误、取消、次数/时间预算、摘要格式重试、分批快照原子性、局部流撤回、手动压缩 SSE 与断线取消、前端倒计时、确认结果幂等键及 SSE 序号恢复。测试使用离线故障注入；本次没有调用付费供应商制造真实故障，也没有部署或重启服务。
